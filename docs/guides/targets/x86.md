# Target guide: x86 (32-bit)

Every command below was run in WSL Ubuntu 24.04 from
a SamCompiler checkout; the output is pasted as it came out,
trimmed only where marked `...`.

## 1. What this target is

| | |
|---|---|
| `-target=` | `x86` (the default when no flag is given) |
| Data model | ILP32: int 4, long 4, pointer 4 |
| ABI | cdecl: every argument on the stack, pushed last first; result in eax |
| Assembler | NASM, `-f elf32` |
| Linker | `i686-linux-gnu-gcc -static`, falling back to `gcc -m32` |
| Runs | natively (the x86-64 kernel runs i386 binaries) |
| Backend | `codegen_x86.c` (the original `codegen.c`) |

This is the target the book teaches. Its output is locked byte for
byte by `tests/176-x86-golden.sh`.

## 2. Prerequisites

```
sudo apt-get install -y gcc nasm gcc-i686-linux-gnu binutils gdb file
```

Do not install `gcc-multilib`: on Ubuntu 24.04 it removes the cross
compilers (see the gotcha below).

## 4. Compile a C file for this target

`/tmp/g/add.c`:

```c
int add(int a, int b)
{
    return a + b;
}

int main()
{
    return add(2, 3);
}
```

```
$ ./main -target=x86 /tmp/g/add.c /tmp/g/add_x86
...
everything compiled fine
nasm -f elf32 /tmp/g/add_x86 -o /tmp/g/add_x86.o && i686-linux-gnu-gcc -static /tmp/g/add_x86.o -o /tmp/g/add_x86
```

`./main /tmp/g/add.c /tmp/g/add_x86` without the flag is the same.
Stop after the assembler with `object`:

```
$ ./main -target=x86 /tmp/g/add.c /tmp/g/add_x86.asm object | tail -2
everything compiled fine
nasm -f elf32 /tmp/g/add_x86.asm -o /tmp/g/add_x86.asm.o
```

## 5. Read the output

```
section .text
global add
add:
push ebp
mov ebp, esp
push dword [ebp+8]              ; a: first argument, above the return address
push dword [ebp+12]             ; b
pop ecx
pop eax
add eax, ecx
push eax
pop eax                         ; return value in eax
pop ebp
ret
```

and the call:

```
lea ebx, [add]
push ebx
pop ebx
mov dword [function_call_1], ebx    ; callee saved in a .data slot
push dword 3                        ; arguments, last first
push dword 2
call [function_call_1]
add esp, 8                          ; caller pops the arguments
push eax
```

with `function_call_1: dd 0` in `.data`.

The frame inside `add`, from gdb (it puts the breakpoint after
`push ebp` / `mov ebp, esp`):

```
$ gdb -q -batch -x gdb32.cmd ./add32
Breakpoint 1 at 0x8049873

Breakpoint 1, 0x08049873 in add ()
0x08049879 in add ()
=> 0x8049879 <add+9>:	pop    %ecx
ebp            0xffffd288          0xffffd288
esp            0xffffd280          0xffffd280
0xffffd288:	0xffffd298	0x0804989e
0xffffd290:	2
0xffffd294:	3
```

`[ebp]` saved ebp, `[ebp+4]` return address, `[ebp+8]` and
`[ebp+12]` the two arguments the caller pushed.

## 6. Assemble and link by hand

```
$ cd /tmp/g
$ nasm -f elf32 add_x86.asm -o add32.o
$ i686-linux-gnu-gcc -static add32.o -o add32
/usr/lib/gcc-cross/i686-linux-gnu/13/../../../../i686-linux-gnu/bin/ld: warning: add32.o: missing .note.GNU-stack section implies executable stack
/usr/lib/gcc-cross/i686-linux-gnu/13/../../../../i686-linux-gnu/bin/ld: NOTE: This behaviour is deprecated and will be removed in a future version of the linker
$ ./add32; echo "exit=$?"
exit=5
```

Static, because the host has no i386 dynamic loader and libc:

```
$ file /tmp/g/add_x86
/tmp/g/add_x86: ELF 32-bit LSB executable, Intel 80386, version 1 (GNU/Linux), statically linked, BuildID[sha1]=57d96a8df70b3a45d42505fd7ba9b0ef7e184218, for GNU/Linux 3.2.0, not stripped
```

### Why not `gcc -m32`

The original driver linked with `gcc -m32`. It needs
`gcc-multilib`, which cannot be installed next to the cross
compilers. Without it:

```
$ gcc -m32 ret42.o -o ret42
/usr/bin/ld: cannot find Scrt1.o: No such file or directory
/usr/bin/ld: cannot find crti.o: No such file or directory
/usr/bin/ld: skipping incompatible /usr/lib/gcc/x86_64-linux-gnu/13/libgcc.a when searching for -lgcc
/usr/bin/ld: cannot find -lgcc: No such file or directory
...
collect2: error: ld returned 1 exit status
$ apt-get install -s gcc-multilib
...
The following packages will be REMOVED:
  gcc-13-aarch64-linux-gnu gcc-13-i686-linux-gnu gcc-13-riscv64-linux-gnu
  gcc-aarch64-linux-gnu gcc-i686-linux-gnu gcc-riscv64-linux-gnu
```

The driver uses `i686-linux-gnu-gcc -static` when it is on the PATH
and only falls back to `gcc -m32` otherwise (`main_link_cmd`,
`link_fallback_cmd` in `target.c`).

## 10. Debug

gdb on the host debugs the static i386 binary directly:

```
$ cat gdb32.cmd
break add
run
stepi 2
x/i $pc
info registers ebp esp
x/2wx $ebp
x/dw $ebp+8
x/dw $ebp+12
$ gdb -q -batch -x gdb32.cmd ./add32
```

(output in section 5). `x/8wx $esp` shows the expression stack.

## 11. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `cannot find Scrt1.o` / `cannot find -lgcc` | linking with `gcc -m32` without gcc-multilib | install `gcc-i686-linux-gnu`; the driver then uses it |
| `Issue assemblign the assembly file with NASM and linking with gcc` | the link step failed, usually the one above | same |
| `missing .note.GNU-stack section implies executable stack` | NASM output has no `.note.GNU-stack` | harmless warning; adding the section would change the locked asm |
| a function returning a struct by value crashed (exit 139) before the fix | the hidden result pointer was pushed before the arguments, not at `[ebp+8]` | fixed: it is pushed last; `tests/181-x86-run.sh` runs that input |
| `176-x86-golden ... FAIL: x86 output for ... differs` | a change moved the x86 asm | if unintended, find it from the printed diff (the left-grouping fix was one); if intended, `tests/golden/regen.sh x86` |
| 135 tests fail with no message right after editing `build.sh` from Windows | the edit dropped the exec bit | `chmod +x build.sh` inside WSL |
